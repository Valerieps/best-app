# ADR-047: Backup folder with dated copies

**Status:** Accepted
**Date:** 2026-10-14
**Decision:** The automatic backup goes to a folder the user picks with `showDirectoryPicker` (`mode: 'readwrite'`), no longer to a single file: the app writes `best-app-backup.json` in it, as before, and keeps dated copies in its `copias` subfolder, named `best-app-YYYY-MM-DD-HHhMM.json` in local time. The rules are pure functions in `application/backupCopies.ts`: before the backup file is rewritten, its previous contents become a copy when they are the last version of an earlier day or come from an older `BACKUP_SCHEMA_VERSION` (data the browser has just migrated); after that, a copy of what is written is saved when today has none from the last 2 hours; then the copies beyond the limits are deleted: the 5 most recent of today, the last of each of the 14 days before, nothing older. Only names matching the copy pattern are ever deleted, and copies dated after today, from another computer's clock, are left alone. The copies are kept only when a write is allowed by the overwrite guard (ADR-008), and a failure in them never stops the backup file: the state reports `copies: 'failed'` and "Dados e backup" says so. Picking a folder goes through the guard too, unlike picking a file (ADR-007): a folder that already has a backup with data the browser lacks blocks instead of being overwritten. A file handle stored before this change keeps working, with `copies: 'off'`, until the user picks a folder. Restoring a copy reads it and goes through the import (ADR-006), which shows what would be lost and can be undone.
**Why:** One file rewritten every few seconds carries any corruption into the only backup at once, and Drive's version history runs out under such frequent writes (issue #28). The owner chose the retention: every 2 hours today up to 5, the last version of each of the 14 earlier days, in a subfolder, deleted by the app, and restorable from "Dados e backup". Creating new files needs permission on a folder, which a file handle does not give; one folder handle covers both the backup file and the copies with a single permission per session. Copying the file's previous contents, rather than writing a separate end-of-day copy, gives each earlier day its true last version without writing twice on every change.
