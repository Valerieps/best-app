# ADR-049: Archiving removed; archived tasks become active tasks without a date

**Status:** Accepted
**Date:** 2026-10-15
**Decision:** The task status `archived` is gone from `TaskStatus`, and so are the `archive` triage decision, `reactivateTask`, the archived tasks screen and the archive step of the Revisão de Foco. The triage gains `{ kind: 'undate' }` ("Sem data"), which removes the intended date through `moveIntendedDate`, so it counts as a postponement like any other removal of the date. Existing data is migrated in both places a record can come from: database version 8 rewrites every block with status `archived`, and backup schema version 8 does the same when an older file is imported. Both use the pure `undateArchivedTask` (`domain/tasks.ts`): status `active`, `intendedDate` and `closedAt` null, everything else kept. The migration records no event and is not a postponement. The event types `task.archived` and `task.reactivated` stay in `EventMap` as history only: nothing emits them any more. The route `#/arquivadas` opens the task list, which can also show the finished tasks ("Mostrar").
**Why:** The owner decided that an undated task already is the "algum dia" (spec/tarefas.md), so the archive was a second place for "not now". A migration event would need an id generator inside a Dexie upgrade and would make the history claim the owner reactivated tasks she never touched; the old `task.archived` events already tell what happened. Counting the migration as a postponement would skew the postponement metrics with a change the owner did not make. Keeping the old event types lets older histories and backups stay valid without rewriting them.
