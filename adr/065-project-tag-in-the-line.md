# ADR-065: The project tag lives in the text by name, and the block's projectId follows it when it changes

**Status:** Accepted
**Date:** 2026-11-10
**Decision:** The project tag (`spec/nota-do-dia.md`, "Tag de projeto na linha") is written in the block's `text`, like the mention (ADR-052), and is read from it by `domain/projectTags.ts`:

- **Syntax.** `#Nome` when the name is one word that starts with a letter (letters, digits, `_` and `-`); `#[Nome com espaços]` for any other name, with `\]` and `\\` inside the brackets for a literal `]` or `\`. The autocomplete writes whichever form the name needs, so I never type the brackets by hand. A `#` only starts a tag at the start of the line or after a character that cannot be part of a word (not after `#` or a letter), so `# ` (heading), `##`, `C#` and `a#b` are no tags. `\#` writes the character, and inside `` `code` `` nothing is a tag, both in the editor and in the derivation, which skip the same escapes and code spans.
- **Name, not id.** The text keeps the project's name, not its id. Outside the day note the text shows as raw Markdown (`spec/nota-do-dia.md`, "Formatação"), in backups and in the "Fechar o dia", and `#Data Studios` must read as such there; an id would show as noise. The cost is the same as the mention's: renaming a project rewrites every tag that pointed to it, and merging projects rewrites the merged project's tags as the kept one's name. Both scan `blocksWithTags()` (every block whose text has a `#`) in the same transaction, with no event per line (ADR-004). Only tags that resolved to that project before the change are rewritten, so a homonym keeps its own tags.
- **Resolution.** A tag points to the project whose name matches it loosely (case, accents and inner spaces ignored, `normalizeForMatch`), among the projects that are not merged; an active one wins over a finished one. A finished project still resolves, so finishing a project does not unlink its lines the next time I edit them; only active projects are suggested. A tag with no project is plain text. When a line has several tags, the first one counts.
- **projectId is still stored.** The block keeps `projectId`, now set by the tag too, because the project page, the task list grouping and the closing all read `blocksOfProject` through the `projectId` index. It is computed by `projectAfterText` whenever a write changes a block's text (create, edit, split, paste, change of kind, restore), and only when the tag changes: a new tag gives the block that project; taking the tag off gives it back the section's project (a task) or none (a note, which keeps following its section). When the tag stays the same, `projectId` is left alone, so a project chosen in the closing for a task of a whiteboard is not undone by fixing a typo. Linking a section to a project, or taking it back to a whiteboard, skips the tasks that have a tag. A change made by the tag records `block.linkedToProject` with `byTag: true`.
- **Notes.** A note's `projectId` was always null: its project was its section's. Now a tagged note carries the tag's project, and the "Notas" tab of a project shows the notes whose `projectId ?? section.projectId` is that project, so a note tagged elsewhere moves out of the section's project into the tagged one.
- **No migration.** No line has a tag before this change, `projectId` already exists on every block, and the new `byTag` is an optional field of an existing event (ADR-043). The database and backup stay at version 10. A `#Word` typed before this change, matching a project, only becomes a tag the next time that line's text is saved.

**Why:** The mention showed that reading links from the text keeps one source of truth across the day note, the project page and backups. The name keeps the raw text readable, and the bracket form is the least surprising way to give a name with spaces an end: matching the longest project name after `#` would make the same text mean different things as projects come and go. Storing `projectId` keeps every existing query and index working; deriving it only when the tag changes keeps the closing's manual choices, which a pure "tag or section" rule would overwrite on each keystroke.
