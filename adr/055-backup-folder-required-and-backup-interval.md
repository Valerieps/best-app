# ADR-055: The backup folder is required before the app opens, and the backup interval throttles instead of debouncing

**Date:** 2026-10-16
**Decision:** `App` renders `BackupSetupScreen` instead of the shell while `needsBackupSetup` (`ui/notices.ts`) holds: the auto backup is `noFile` or `unsupported`. Nothing renders while it is `loading`, so the app never flashes before the screen. Every other state, including `needsPermission`, `blocked` and `error`, opens the app with the existing warnings. The interval lives in `Settings.autoBackupInterval` (`afterChange`, `quarterHour`, `hour`; absent means `afterChange`), so it travels with backups, and `App` hands it to `AutoBackup.setInterval`. `autoBackupWait` (`application/autoBackup.ts`) gives each interval a wait and whether a change restarts it: `afterChange` keeps the 3-second debounce; the intervals start the wait on the first change and later changes join it. `AutoBackup.onHidden` replaces the direct `flush` on `visibilitychange`: it writes right away only with `afterChange`; with an interval the pending change waits, and `init` already catches up when the app opens again.
**Why:** The owner wants the folder chosen before any use (spec/principios.md, "Primeiro uso"), and the File System Access API exists only in Chromium on desktop, so another browser cannot pass the screen. Debouncing an hour-long wait would never write while the user keeps working, hence the throttle. Writing on every hide would defeat a longer interval, since switching tabs hides the page; skipping it costs nothing, because the data is still in IndexedDB and the next opening writes it.
