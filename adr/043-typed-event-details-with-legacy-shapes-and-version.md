# ADR-043: Typed event details, with legacy shapes and a version

**Status:** Accepted
**Date:** 2026-10-14
**Decision:** `src/domain/events.ts` maps each event type to the shape of its `data` (`EventData`), and `DomainEvent` is a union discriminated by `type`, so checking the type narrows `data`. The list of event types is the keys of that map. `record` is generic over the type and only accepts its shape: details are required unless the type carries none (`EventTypeWithoutData`), and a misnamed field, an unknown value of a closed set (such as the reason of a date change) or details on a type without them fail to compile. `src/application/events.test.ts` holds `@ts-expect-error` lines that `npm run build` typechecks, so the build fails if `record` stops rejecting them. Shapes the app wrote before and no longer writes live in `LegacyEventData`, found by reading every `record` call in the git history: the weekly and monthly `reflection.closed` (`week` or `month` instead of `kind` and `since`) and the week lists of `priority.added` and `priority.removed` (with `week`). An event read from the history has either shape. Fields added to a shape after it was first recorded are optional (`block.created` with `projectId`, `section.created` with `projectPage`). Events gain an optional `v`, the version of their shape: absent means 1, the only version so far, so nothing is migrated and the database and backup versions stay the same. A shape already recorded never changes: a new field is optional, and an incompatible change moves the old shape to `LegacyEventData` and bumps `EVENT_DATA_VERSION`. Readers that use a field keep checking its value (`itemIdsOf` in `focusProjects.ts`, the `intendedDate` of `task.finished` in `metrics.ts`), since an imported backup is not validated event by event.
**Why:** Events are never edited, so a field written under the wrong name, or a shape that changes silently, leaves history that later metrics cannot read, and before this nothing but convention tied the writers to the readers (issue #52). Typing the writes closes that door for new events at no runtime cost. Typing the history cannot make old or imported events correct, which is why the legacy shapes are declared and the readers stay defensive. The version is optional and absent today so the change needs no schema migration; it exists so that the first incompatible change has a way to tell old events from new ones.
