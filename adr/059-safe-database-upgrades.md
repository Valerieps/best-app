# ADR-059: Safe database upgrades: snapshot, version gate, no rollback

**Status:** Accepted
**Date:** 2026-10-16
**Decision:** Every change to the IndexedDB schema follows these rules:
1. **Snapshot first.** Every `upgrade` function in `src/infrastructure/db.ts` calls `snapshotBeforeUpgrade` before changing any row. It copies every user table, as the previous version left it, into `snapshots` under the id `beforeUpgrade`, in the same transaction. When several versions upgrade in one go, only the first copy is kept. A new database takes no copy.
2. **Version gate.** `DATABASE_VERSION` names the last declared version (a test checks it). At startup, `watchDatabaseVersion` compares it with the installed version: a database newer than the code is closed with auto-open disabled, and the app shows "O app foi atualizado" with a reload button instead of the screens. When another tab upgrades the database (`versionchange`), Dexie closes this tab's connection and the same screen asks for a reload.
3. **Expand, then contract.** A version only adds tables, indexes or optional fields. Removing or renaming a field takes two releases: the first stops reading it, the next one drops it. Code reads unknown fields and missing optional fields without failing. Event types and their payloads in the history never change meaning; a new shape is a new type.
4. **Two paths, one migration.** Each Dexie upgrade has its twin in `upgradeTables` (`src/application/backup.ts`), so an old backup imports to the same result, and each gets a unit test that starts from the old version.
5. **Roll forward, never back.** A deployed database version is never rolled back on Cloudflare Pages: the older code would face a newer database (rule 2 stops it, but the app stays closed until a fixed version ships). A bad release is fixed by a new version.
**Why:** The data lives only in the user's browser. A migration with a bug changes it in place, with no server copy to fall back on; the automatic backup in the folder may be days old, depending on its interval (ADR-056). The service worker activates a new version at once (`skipWaiting`, `clients.claim`), so a tab still running the old code can meet a database the new code already upgraded. Dexie 4 opens a database newer than its schema without an error, so without the gate old code would write rows the new code does not expect.
**Not done here:** a screen to restore the `beforeUpgrade` copy, and clearing it after some time; tracked in issues #134 (restore and cleanup), #135 (migration twin test) and #136 (backup before an upgrade).
