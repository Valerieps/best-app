# ADR-048: Markdown per line, kept as plain text and parsed in the app

**Status:** Accepted
**Date:** 2026-10-15
**Decision:** The day note supports a small Markdown subset per line: headings `#` to `####`, bullet (`- `, `* `, `+ `) and numbered (`1. `) list items with two spaces of indentation per level (up to 4), bold `**x**`, italic `_x_` or `*x*`, links `[x](url)` and bare `http(s)` addresses. The block's `text` keeps the raw Markdown: no new field, no event, no schema or backup version. A small parser of our own (`ui/dayNote/markdown.ts`, pure functions) reads a line into nodes that `MarkdownText` renders as React elements; link targets are limited to `http`, `https` and `mailto`, and open with `target="_blank" rel="noopener noreferrer"`. The same module edits a line with its selection (`applyFormat`), shared by the keyboard shortcuts and the section toolbar. While a line has no focus and has something to format, `BlockLine` shows the formatted view and keeps its textarea in the DOM, invisible, so focus requests (ADR-014) and the keyboard still reach it; on focus the raw text comes back. The toolbar, in the section header, reaches the focused line through a DOM `CustomEvent` (`line-format`) instead of lifting each line's text state up to the screen.
**Why:** One textarea per block (ARQUITETURA.md, section 3) rules out a document editor such as ProseMirror, and the per-line syntax fits one block per line. A Markdown library would bring HTML output that we would have to sanitize, or a renderer bigger than the subset we need, against `SEGURANCA.md`'s rule to minimize dependencies and never insert user text as HTML. Keeping the text as plain Markdown leaves backups, the wiki and the checkout readable, and lets the formatting later reach those screens without migrating data. The DOM event keeps `BlockLine` owning its unsaved text and save timer, as it already does for typing.
