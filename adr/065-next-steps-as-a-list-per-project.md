# ADR-065: Next steps as one list per project in `priorities`

**Status:** Accepted
**Date:** 2026-11-10
**Decision:** A project's next steps (up to 3 tasks) are one record in `priorities`, id `next:<projectId>`, scope `nextSteps`, no period, copying the list in focus (ADR-038). No database or backup version change: the table already exists and `scope` is not validated. Use cases in `application/nextSteps.ts`: `setNextStep(taskId, on)` marks or unmarks; marking a fourth keeps the first two and appends the new one, so it takes the place of the third (as `promote` does for the day priorities). `releaseNextStep(tx, task, reason)` takes a task out when it is finished (`finishTaskIn`), abandoned (every path: note, checkout, assistants, planning), converted to a habit, or leaves the project (`setTaskProject`, the checkout's project link, linking or unlinking a section, merging projects); it is called with the task as it was before the change and does nothing when the task is not in the list. Each change records `priority.added` or `priority.removed` on the entity `next:<projectId>` with `{ taskId, projectId, itemIds }`, plus `replaced` on an addition that took a place and `reason: 'removed' | 'finished' | 'abandoned' | 'moved'` on a removal. Reading never trusts the stored ids: `nextStepIds` shows only tasks that are still open, still tasks and still in the project, so a path that did not release (a note made from the task, a deleted line) simply stops showing it. Only an open, non-waiting task of a project can be marked. Reopening a task does not bring the mark back. `ProjectView.nextStepIds` feeds the page; `TaskListContext.nextStepIds` feeds the task list, which reads every `next:` list with one range query.
**Why:** The spec asks for the same shape as the projects in focus: a small ordered list, one event per change, history from the events. A list per project (and not a flag on the block) keeps the order marked and the "fourth takes the third" rule in one place and needs no migration. Releasing eagerly keeps the stored list honest, so a place is never held by a task that cannot be a next step; filtering on read is the safety net for paths that bypass the use cases (backup import, a conversion to note).
