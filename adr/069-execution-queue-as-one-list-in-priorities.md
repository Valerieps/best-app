# ADR-069: Execution queue as one list in `priorities`

**Status:** Accepted
**Date:** 2026-11-12
**Decision:** The "Fila de execução" (spec/prioridades.md) is one record in `priorities`, id `queue`, scope `queue`, no period, no size limit, copying the next steps (ADR-065). No database or backup version change: the table exists and `scope` is not validated. Use cases in `application/executionQueue.ts`: `addToQueue` appends an open, non-waiting task at the end; `removeFromQueue` takes it out by hand; `reorderQueue(shownIds, movedId)` saves the order after a drag; `releaseFromQueue(tx, task, reason)` runs next to `releaseNextStep` wherever a task is finished or abandoned (note, checkout, assistants, conversion to habit). Adding and removing record `priority.added` / `priority.removed` on the entity `queue` with `{ taskId, itemIds }`, plus `reason: 'removed' | 'finished' | 'abandoned'` on a removal. Reordering records no event, like every other reorder (ADR-040); the next addition or removal carries the whole list. Reading never trusts the stored ids: `queueIds` shows only open, non-waiting tasks, so a task that turned waiting simply stops showing. A drag sees only the shown ids, so `reorderedQueue` keeps hidden recorded ids in the list and puts the moved one right after the shown task that now precedes it. The screen replaced "Executar"; its route keeps the name `execute` and `domain/execute.ts` was removed.
**Why:** Same shape as the other small ordered lists: history from the events, no migration, no flag on the block. Waiting tasks stay recorded but hidden, so turning one back into my task brings it back in place without a rule of its own.
