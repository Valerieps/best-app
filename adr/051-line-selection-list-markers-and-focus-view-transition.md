# ADR-051: Selecting whole lines, list markers outside the field, and focus mode as a view transition

**Status:** Accepted
**Date:** 2026-10-15
**Decision:** Three changes to the day note editor, all in `ui/dayNote`, with no schema, event or backup change.
- **Selecting lines.** The browser's selection cannot span several textareas, so `useLineSelection.ts` selects whole lines instead: a press inside a line keeps selecting text natively until the pointer reaches another line (found with `elementFromPoint` and the lines' `data-drag-id`), Shift + click selects from the line with the cursor, and Ctrl + A with the line's whole text already selected selects every line. While lines are selected, the note container (`tabIndex=-1`) holds the focus and handles the keys: copy and cut write plain text with `navigator.clipboard.writeText`, delete runs `deleteBlock` on the free lines only. The order of the lines is read from the DOM, so it is always the order shown, also in focus mode. The pure parts (ranges, Ctrl + A, the copied text) live in `blockSelection.ts`.
- **List markers.** A list item's prefix (indentation and marker) stays in the block's text, but the textarea holds only what follows it, and `ListMarker` draws the marker beside it. The field is always wrapped in `.line__field`, so it is never remounted (losing the focus) when a line becomes a list item. Carets and selections handed between lines stay counted on the whole line; `BlockLine` and `useFocusTarget` subtract the prefix. `* ` and `+ ` are rewritten to `- ` on input.
- **Focus mode transition.** Entering and leaving focus mode runs inside `document.startViewTransition` (`focusTransition.ts`). The part being focused carries the same `view-transition-name` (`focus-part`) on both screens, so the browser animates it between its place in the note and the whole screen, and the rest cross-fades. The update callback waits until the screen commits the new focus (a layout effect), or 800 ms at most, since the browser freezes the screen during that wait. Without View Transitions, or with `prefers-reduced-motion`, the previous CSS fade stays.
**Why:** Turning the editor into one contenteditable document would break the one-record-per-block rule (ARQUITETURA.md, section 3) and need a document editor library, against `SEGURANCA.md`'s rule to minimize dependencies; selecting whole lines covers the need, as block editors such as Notion do. Hiding the marker in the field keeps the stored Markdown unchanged (ADR-048) while the line looks like a list as soon as it becomes one. The View Transitions API is built into Chrome, needs no dependency, and animates between two different trees (the whole note and the focused part), which a CSS animation on one tree cannot do; the focus change is asynchronous (it is saved in the settings, ADR-046), hence the bounded wait.
