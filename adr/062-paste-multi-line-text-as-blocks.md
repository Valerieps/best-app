# ADR-062: Pasted text with line breaks becomes one block per line

**Status:** Accepted
**Date:** 2026-11-04
**Decision:** The line editor (`BlockLine`, `GhostLine`) handles `paste`. Plain text with a line break never goes into the textarea as it is. It is split by `pastedLines` (`src/ui/dayNote/paste.ts`): line breaks `\r\n`, `\r` and `\n` are normalized, **blank lines are dropped**, trailing spaces are cut and leading tabs become two spaces (list depth). `applyPaste` then builds the lines: the first pasted line joins the text before the caret (the selection is replaced), the text after goes to the end of the last one, and the caret lands in the last line. The first line goes through `detectKind` only when the line is a free note and not a kept project note; the new lines go through it unless `notesOnly`. `pasteLines` (existing line) and `createBlocks` (empty ghost line) save the whole paste in one transaction. **Maximum: 300 lines.** Above it, and where lines cannot be created (`allowNewLines` false, no handler), the lines are joined with single spaces into the current line, so no text is lost. On a project page the new lines are kept notes (created like `splitKeptNote`, without reopening a triage). An address pasted over a selection makes the selection a link.
**Why:** One line is one block: closing the day, triage, multi-line selection and kind detection all treat a block as one line. A textarea holding line breaks broke that silently. Blank lines would make empty notes that the person did not choose, and a paste of thousands of lines would write thousands of records and rerender the note at once; the cap keeps it bounded without dropping text. Positions are chained between the neighbors (`chainedPositions`) so the pasted lines stay in order. The save path was checked and does not lose multi-line text (`multilineText.test.ts`); the earlier "only the first line came back after Ctrl+Z" report was the browser's undo (ADR-063).
